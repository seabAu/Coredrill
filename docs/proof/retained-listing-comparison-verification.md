## Data and trust boundaries

The comparison query validates one job, two distinct explicitly chronological snapshot IDs, archive scope and operation time. It drains both original-capture reads before returning a failure, including a synchronous early throw. Each underlying capture query revalidates the original retained envelope and both semantic/full-envelope hashes. Comparison checks returned scope/identity/time/fingerprint and never uses current field-review or accepted requirement rows. Equal/reversed capture instants do not establish change order and fail visibly.

The runtime composes the already-selected `@coredrill/extractors` package with the application query. Normal captures can retain JSON-LD without structured candidates, so comparing original candidate rows alone would miss useful facts. The existing Schema.org adapter re-analyzes retained JSON-LD or explicit JSON-LD inside a saved JSON payload; payload pointers are remapped to the actual `/content/apiPayload` coordinates. No arbitrary API payload is guessed into a connector format, no HTML is executed, no source is fetched and no provider/AI operation exists. The normalization contract is revalidated; every original candidate must survive unchanged, and derived candidates must retain the same capture ID/time. Current-analysis facts have `candidateId: null`, not a fabricated stored candidate reference. Their origin, analyzer version and analysis time are explicit.

Only an internal workspace link is added to the web app, its project references and prebuild/predev composition. Offline lockfile generation/frozen installation downloads and adds zero external packages; the lockfile diff is exactly the three-line internal link. No external version, migration, durable contract, extension permission or Accepted decision changes.

## Comparison semantics

Requirements, compensation, deadline and locations each retain separate before/after states: known, missing, ambiguous or unavailable. Only two known projections can be unchanged/changed. Missing extraction never becomes an empty set, a removed field or a zero-change aggregate. There is no overall score or change count that could hide incomplete fields. Content comparison separately names recorded capture fingerprints, not a new body-integrity certificate.

Requirements compare retained extraction/line slots, not inferred identity between similar prose. Their exact source blocks remain JSON literals, including object/markup-shaped source values; no semantic HTML rendering or inferred category promotion occurs. Current text analysis reuses requirement-parser spec 1 over retained snapshot text, with its existing bounded lines/blocks/excerpts. Different original/current-analysis profiles are not silently compared as the same requirement basis. Explicit retained empty requirement arrays carry separate literal absence evidence and no invented confidence; missing properties do not. A conflicting nonempty plain-text analysis is ambiguous rather than discarded in favor of the empty array.

Compensation preserves normalized decimal bounds, minor units, explicit currency and currency scale, and interval without currency conversion or annualization. Partial or conflicting candidates are ambiguous. Deadline precision is preserved instead of truncating instants to dates. Locations compare normalized facts as sets while keeping physical, remote-region and literal-label precision distinct. Exact original/raw serialized values, pointers, excerpts, extractor identity, method and confidence remain beside normalized values. Known means usable retained comparison evidence, never employer verification or user confirmation.

The existing JSON-LD extractor can omit an invalid sibling without warning when another entry survives. A focused regression reproduced a false unchanged salary result. The runtime now checks coverage of exact retained field coordinates after the extractor's own bounded validation: an unrepresented salary, requirement, deadline or location sibling makes that field uncertain. This does not change the existing extractor version/goldens or create a second value extractor. Multiple discovered postings also remain uncertain even when their candidate values agree.

Capture reads retain the explicit 2 MiB / 20,000-value / 40-level boundary. The existing extractor/normalizer keep their own 10,000-value / 32-level / 256-candidate limits; normalization output is additionally bounded to 4 MiB before application validation. Known analysis-limit failures become unavailable, never partial/empty success. Text parser limits stay explicit. Output is copied/frozen ephemeral evidence, not another canonical store. Literal `refreshPerformed` and `trustedFieldMutationPerformed` remain false.
