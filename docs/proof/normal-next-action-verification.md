## Requirements and observed regressions

- Interactive creation must carry the viewed job version, not read a replacement version only after submission; archived jobs reject even when the supplied version is current.
- Rejection must leave job, action and undo-token records exactly unchanged.
- Creation adds a pending task. Existing tasks remain pending. The maintained due projection must match the earliest scheduled pending task already selected by Pipeline reads and recomputed by completion.
- Unscheduled tasks retain null due instant and time zone. Adding unscheduled, later or earlier tasks and undoing each must preserve coherent projections.
- Undo retains existing row-version/replay safety and dismisses the created action and linked pending reminders, without deleting history.

## Normal-UI composition audit (2026-10-20)

The [exact candidate review](next-action-timezone-candidate-review.md) executes DST probes for date-fns 4.4.0/date-fns-tz 3.2.0 in an isolated scripts-disabled directory, without changing product dependencies. It finds silently shifted gaps and a repeated New York clock time resolving to different UTC instants under different host zones. The host-independence assertion remains failing; direct conversion and round-trip-only validation are not suitable normal scheduling proof. No substitute library or Accepted decision change is made.

- The new runtime is not yet exposed by `CoredrillStorageSpikeApi` or composed in `main.ts`; the normal header still only announces its next-action selection. Those are unfinished integration points, not successful task writes.
- `useStoredStatusActions` currently owns the single-flight lock, canonical Pipeline refresh and durable undo entries. Task creation must join that owner rather than introduce a competing lock. Undo entries and feedback need explicit mutation kind so task undo never claims to restore a status or append a status event. Existing Board/Table/header status safeguards must remain covered.
- Root-owned next-action drafts must capture job identity/version before asynchronous work, retain exact title and scheduling choices on failure, survive tabs/responsive frame replacement, reject stale context without rebasing, prevent foreign-job submission, and avoid late acknowledgement/focus publication into another job. Cancel/discard cannot abandon an in-flight write.
- A local date/time plus IANA zone can identify zero or multiple instants. [TC39's ZonedDateTime documentation](https://tc39.es/proposal-temporal/docs/zoneddatetime.html) specifies explicit disambiguation/overflow behavior; silent default clock adjustment is unsuitable for the form. [Chromium's shipping record](https://groups.google.com/a/chromium.org/g/blink-dev/c/s58GKzoQZFg/m/ls3hqsLaAAAJ) and [Firefox 139 release notes](https://www.mozilla.org/firefox/139.0/releasenotes/) establish implementations, not all accepted native-WebView coverage. The actual pinned Node 24.19.0 reports `typeof Temporal === "undefined"`. Native Temporal alone is therefore not a cross-runtime implementation plan.
- Technology document 10, read completely for this audit, already selects `date-fns` plus `date-fns-tz`; neither is installed in the current lockfile. The [maintainer's time-zone documentation](https://github.com/marnusw/date-fns-tz#time-zone-offset-helpers) describes Intl-based conversion without bundled zone data, but does not by itself prove the required ambiguous/nonexistent-time handling. Before adding either package, review exact current versions, license/security/bundle impact and executable DST cases. No library/platform substitution, dependency installation or new support promise occurs in this audit, and no owner decision currently blocks the review.
