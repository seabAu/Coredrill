## Read-only directory prerequisite review

Subsequent exact scheduling follow-up `bc28c8a` / `39625297012` is live. Product source remains frozen while it is verified; the following is a candidate next bounded slice, not an implemented contract or a completed Network item.

- `CompanyContactPort` only creates companies/contacts and copies validated create acknowledgements. Its company DTO includes full private notes and has no archive field because the operation only creates active rows. Reusing it as a directory response would overfetch notes and misrepresent archive state. Define a separate versioned, minimized read-page DTO rather than broaden creation semantics.
- Company/contact tables live inside one vault database, not per-row vault foreign keys. A directory request must carry the explicitly viewed vault identity, copy it before awaited work and verify the actual vault root in the same read transaction. A wrong/missing vault must not return another database's companies, create setup data or trigger browser fallback from a failed native runtime.
- Bound page size and result size, validate exact request/response/cursor versions and scope, reject unknown/malformed fields and duplicate/out-of-order identities, copy/freeze results and redact private port errors. Default active scope must remain explicit; archived results need honest state. Future detail reads may expose selected notes/contact points with their actual provenance, not hidden private fields in every summary.
- Existing `job-next-actions` application/storage queries provide scoped cursor-anchor/version validation and transactional page patterns, but their job revision cannot be invented for the whole company directory. Cross-page reads must be described as live pages, not an immutable historical snapshot. A wall-clock `created_at <= now` ceiling would silently omit valid imported/future-dated local records, so it must not be adopted as a false consistency guarantee. Review keyset/index behavior explicitly before implementation.
- The existing `job_company_active_idx` supports saved active-job relationships. No company-directory ordering index or contact-company index is currently present. Output bounds alone do not prove reference-hardware latency; retain that limitation and measure before claiming a performance budget or adding a migration solely by assumption.
- Minimum proof for the prerequisite is application input/result/cursor/error/ownership mutation tests and a shared actual-SQLite repository case for active/archive pages, equal sort keys, original-vault rejection, changed/deleted cursor anchors, exact inert names, private-error redaction and unchanged canonical data. Node-only tests or reference catalog rendering cannot establish browser/native or complete Network integration. Normal route, empty/loading/error/retry, explicit manual creation, contacts, interactions, offline/reload/reflow and native integration still follow separately.

## Catalog composition traps to avoid

The complete 967-line `packages/ui/src/network-workspace.tsx` was read for this review. Its current rich catalog model cannot be filled with placeholder arrays and treated as a truthful paged stored view:

- Displayed job/contact/interaction/salary totals are array lengths and the component's empty messages assert absence. Empty arrays for relationships that have not been queried would invent zero totals and false “no records” claims. Explicit loading/unavailable/paged states or separately validated totals are needed.
- `hasIdentity` limits company/contact names and job titles to 128 characters, while existing application contracts accept company/contact names up to 512. The component also requires HTTPS website links, while the durable `webUrl` contract accepts credential-free HTTP or HTTPS. Integration must not silently truncate valid stored names, discard URLs, upgrade schemes or crash the whole directory to fit a catalog constraint.
- Contact identity/contact-point origins require explicit user-entered/public/licensed basis and source links for non-manual values. The existence of a generic provenance row or `userConfirmed` bit does not by itself establish a public/license right. Never relabel source-backed fields as explicitly public merely to populate this model, and do not fabricate a web URL for local-document evidence.
- The component validates that every contact/interaction company identity is in its loaded company array. Independently paged directories can legitimately reference a company outside the current page; forcing a complete vault preload or falsifying that linkage is not a safe adapter.
- Its interaction composer currently trims and clears the summary immediately after a synchronous optional callback, not durable acknowledgement. Normal creation must use an owned draft/single-flight/error/readback coordinator, retain exact supported input on failure and distinguish recorded local history from sending anything. Existing catalog action announcements do not prove persistence.

These are integration mismatches and missing states, not authorization to weaken provenance/source policy or change an Accepted architectural decision. The minimized directory prerequisite remains smaller than a full replacement of this model, and none of these findings closes Network or changes product code.

Subsequent read-only runtime review confirms `createStoredPipelineApi` composes application validation around a lazily selected actual database, while `main.ts` supplies the selected database/migration and runtime-owned operation context. A future separate directory API should preserve validation before opening storage and carry the original viewed vault explicitly, rather than derive a replacement owner after awaiting. The existing `createStoredJobDetailsReader` demonstrates disposable single-flight read coordination and retained values on failed refresh; directory paging additionally needs explicit continuation ownership and cross-page duplicate/change handling without claiming a frozen snapshot or a total from loaded arrays. These observations do not implement runtime/UI composition. The query prerequisite is now separately scoped and implemented under [its own proof](company-directory-prerequisite-verification.md); the original no-implementation statements in this audit describe the earlier read-only checkpoint.
